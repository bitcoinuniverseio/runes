Normative Protocol Specification

Runes Protocol Specification

Normative consensus specification for the Runes protocol on Bitcoin, numbered rules R1 through R47, tag dictionaries, and cenotaph flaw definitions.

Pinned to Casey Rodarmor's ord 0.29.0 (ordinals crate 0.0.17, commit 7e37a3b) · Activation Block: 840,000.

This document constitutes the authoritative, normative specification of the Runes protocol on Bitcoin. Every numbered statement (R1 through R47) defines an immutable protocol rule verified by consensus indexers.

Zero External Dependencies

Runes is fully self-contained on the Bitcoin blockchain. It does not use witness data, external state commitments, off-chain DA layers, or second-layer sidechains. All state transitions derive purely from transaction inputs, outputs, and OP_RETURN script pushes.

1. Carrier Output

A transaction communicates protocol messages through a standard Bitcoin data carrier output.

R1: OP_RETURN and OP_13 carrier script

[1. Carrier and transaction anatomy]

A runestone is carried in a transaction output whose script begins with OP_RETURN (0x6a) followed immediately by OP_13 (0x5d, also written OP_PUSHNUM_13), the Runes protocol identifier.

ord Source: crates/ordinals/src/runestone.rs

R2: First matching output is selected

[1. Carrier and transaction anatomy]

Outputs are examined in order. The first output matching R1 is the transaction's runestone. A transaction has at most one runestone; once one is found, no later output is examined.

ord Source: crates/ordinals/src/runestone.rs

R3: Non-matching outputs are skipped

[1. Carrier and transaction anatomy]

Outputs that do not match R1 are skipped when searching, including outputs whose scripts do not parse and OP_RETURN outputs without the OP_13 identifier. They never make the transaction invalid.

ord Source: crates/ordinals/src/runestone.rs

R4: Payload concatenation of data pushes

[1. Carrier and transaction anatomy]

The runestone payload is the concatenation, in order, of the contents of every data push after OP_13. All pushdata opcodes are legal: OP_0 (0x00, empty push), direct pushes 0x01 to 0x4b, OP_PUSHDATA1 (0x4c), OP_PUSHDATA2 (0x4d), and OP_PUSHDATA4 (0x4e). Zero pushes is legal and yields an empty runestone.

ord Source: crates/ordinals/src/runestone.rs

R5: Non-pushdata opcode yields Opcode flaw

[1. Carrier and transaction anatomy]

Any non-pushdata opcode (0x4f and above, including OP_PUSHNUM opcodes) after OP_13 makes the transaction a cenotaph with flaw Opcode.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: Opcode

R6: Unparseable script yields InvalidScript flaw

[1. Carrier and transaction anatomy]

A script that fails to parse after OP_13 (for example a push length running past the end of the script) makes the transaction a cenotaph with flaw InvalidScript.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: InvalidScript

R7: Output value unconstrained

[1. Carrier and transaction anatomy]

The protocol does not constrain the runestone output's value in satoshis. It is conventionally zero, since OP_RETURN outputs are unspendable.

ord Source: crates/ordinals/src/runestone.rs

2. Integers and Varints

All integers inside a Runestone payload are encoded using unsigned LEB128 varints.

R8: Unsigned 128-bit LEB128 varints

[2. Varint encoding]

The payload decodes into a sequence of unsigned 128-bit integers encoded as LEB128 varints: each byte contributes its low 7 bits, least significant group first; a set high bit (0x80) means another byte follows.

ord Source: crates/ordinals/src/varint.rs

R9: 19-byte limit and overflow mask

[2. Varint encoding]

A varint is at most 19 bytes long. Decoding fails as Overlong past 19 bytes, as Overflow when the 19th byte carries bits above the 128th (19th byte value with any of mask 0b0111_1100 set), and as Unterminated when the payload ends with the continuation bit set.

ord Source: crates/ordinals/src/varint.rs Violating Flaw: Varint

R10: Varint decoding failure produces Varint flaw

[2. Varint encoding]

Any varint decoding failure anywhere in the payload makes the transaction a cenotaph with flaw Varint. The whole payload must decode.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: Varint

R11: Non-minimal varints accepted

[2. Varint encoding]

Non-minimal encodings decode successfully: 0x80 0x00 decodes to the same integer as 0x00. Encoders should emit minimal encodings; decoders must accept both.

ord Source: crates/ordinals/src/varint.rs
LEB128 Encoding vs Decoding Asymmetry

Under Rule R10, indexers accept non-minimal LEB128 encodings (such as 0x80 0x00 for zero). However, under Rule R11, serializers should always emit the minimal representation to conserve byte budget within the standard 83-byte relay limit.

3. Message Structure

The integer stream is partitioned into tag-value pairs followed by an optional edicts body.

R12: Tag and value pairs

[3. Message structure]

The integer sequence is parsed front to back as tag and value pairs: even positions are tags, the following integer is the value, until the Body tag (0) is reached.

ord Source: crates/ordinals/src/runestone/message.rs

R13: Trailing tag produces TruncatedField flaw

[3. Message structure]

A tag at the end of the sequence with no following value makes the transaction a cenotaph with flaw TruncatedField.

ord Source: crates/ordinals/src/runestone/message.rs Violating Flaw: TruncatedField

R14: Tag value queues

[3. Message structure]

Repeated occurrences of the same tag accumulate their values in order into a queue for that tag. Interpretation consumes values from the front of the queue.

ord Source: crates/ordinals/src/runestone/tag.rs

R15: Edicts in groups of four

[3. Message structure]

Everything after the Body tag is edict data, in groups of exactly four integers: block delta, transaction index (or delta), amount, output. A final group of fewer than four integers makes the transaction a cenotaph with flaw TrailingIntegers.

ord Source: crates/ordinals/src/runestone/message.rs Violating Flaw: TrailingIntegers

4. Tag Dictionary

Tags identify message fields. The parity of the tag determines indexer behavior when encountering an unrecognized field.

2 Flags even 1 Bitfield: bit 0 Etching, bit 1 Terms, bit 2 Turbo, bit 127 reserved (R18). (R18)
4 Rune even 1 The etched rune's name as a base-26 integer (R21). Requires the Etching flag. (R21)

R16: Odd tags are informational

[4. Tag table]

Odd tags are informational. Unrecognized odd tags, duplicate odd-tag values beyond those consumed, and odd-tag values that fail their range checks are silently ignored.

ord Source: crates/ordinals/src/runestone.rs

R17: Unconsumed even tag produces UnrecognizedEvenTag flaw

[4. Tag table]

Even tags must be understood and fully consumed. If any even-tag value remains unconsumed after interpretation, the transaction is a cenotaph with flaw UnrecognizedEvenTag. This covers: unrecognized even tags (including reserved tag 126), even fields present without the flag that enables them, duplicate values beyond a field's arity, a Mint tag with only one value, and even-tag values that fail a range check (for example a Pointer not less than the output count, or a HeightStart above u64).

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: UnrecognizedEvenTag

5. Flag Bitfield

The Flags field (Tag 2) contains a bitfield controlling etching, open mint terms, and protocol flags.

Flag BitNameMaskMeaning
0Etching0x01 (1 << 0)Transaction etches a new rune. Enables Tags 1, 3, 4, 5, 6.
1Terms0x02 (1 << 1)Etching includes open mint terms. Enables Tags 8, 10, 12, 14, 16, 18.
2Turbo0x04 (1 << 2)Opts the etched rune into future protocol rule additions.
127Cenotaph1 << 127Reserved for future cenotaph signaling.

R18: Flag bitfield values

[5. Flags]

The value of tag 2 is a bitfield. Bit 0 (Etching): this runestone etches a rune. Bit 1 (Terms): the etching has open mint terms. Bit 2 (Turbo): the etching opts in to future protocol changes. Bit 127 (Cenotaph): reserved, never valid.

ord Source: crates/ordinals/src/runestone/flag.rs

R19: Unrecognized flag bit produces UnrecognizedFlag flaw

[5. Flags]

The Terms and Turbo flags are consumed only when Etching is set. Any flag bit still set after consumption, including Terms without Etching or any unassigned bit, makes the transaction a cenotaph with flaw UnrecognizedFlag.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: UnrecognizedFlag

6. Etching

An etching creates a new fungible token on Bitcoin. It may be an open mint, premined, or fixed supply.

R20: Etching fields and immutability

[6. Etching]

An etching is present exactly when flag bit 0 is set. Its fields, all optional, are Rune (4), Divisibility (1), Spacers (3), Symbol (5), Premine (6), and, when the Terms flag is also set, Amount (10), Cap (8), HeightStart (12), HeightEnd (14), OffsetStart (16), OffsetEnd (18). Once etched, all properties are permanently immutable.

ord Source: crates/ordinals/src/etching.rs

R21: Modified base-26 name encoding

[6. Etching]

Names are sequences of the letters A through Z, encoded as an integer in modified base 26: for each letter after the first, add one, then multiply by 26 and add the letter's index (A is 0). A is 0, B is 1, Z is 25, AA is 26, AB is 27, and so on. Decoding reverses this: add one, then repeatedly take (n - 1) % 26 as the last letter and continue with (n - 1) / 26.

ord Source: crates/ordinals/src/rune.rs

R22: Reserved names threshold

[6. Etching]

All name values at or above 6402364363415443603228541259936211926 (the value of 27 letters A) are reserved. Consequently, etchable names are 1 to 26 letters long.

ord Source: crates/ordinals/src/rune.rs

R23: Divisibility maximum 38

[6. Etching]

Divisibility is the number of decimal places, at most 38. A larger value fails the range check and is ignored: the etching proceeds with default divisibility 0.

ord Source: crates/ordinals/src/runestone.rs

R24: Spacers bitmap formatting

[6. Etching]

Spacers are a bitmap: bit i set places a dot • after letter i + 1. The maximum accepted value is 0x07FFFFFF; larger values are ignored. Spacers are display only: a name's identity and uniqueness ignore spacers, spacers may only fall between letters, and they do not count toward name length.

ord Source: crates/ordinals/src/spaced_rune.rs

R25: Unicode scalar currency symbol

[6. Etching]

The symbol is a single Unicode scalar value. Values that are not valid scalars (above U+10FFFF or in the surrogate range) are ignored. A rune with no symbol is displayed with the generic currency sign ¤.

ord Source: crates/ordinals/src/runestone.rs

R26: Premine joins unallocated pool

[6. Etching]

The premine is allocated to the etching transaction as unallocated runes, exactly as if it had been an input balance, and is assigned to outputs by the same edict and pointer rules.

ord Source: src/index/updater/rune_updater.rs

R27: Supply overflow produces SupplyOverflow flaw

[6. Etching]

Etching supply must fit: premine + cap * amount computed in u128 must not overflow. Overflow makes the transaction a cenotaph with flaw SupplyOverflow.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: SupplyOverflow

R28: Etching commitment and eligibility preconditions

[6. Etching]

An etching with a name is honored by the indexer only if all of the following hold at indexing time; otherwise the etching is disregarded entirely (this is not a cenotaph): (1) the name's value is at least the minimum unlocked at the etching block height (R30); (2) the name is not reserved (R22); (3) the name has not already been etched, ignoring spacers; (4) the transaction commits to the name: some input spends a pay-to-taproot output, that input's witness contains a tapscript with a data push exactly equal to the name's value as little-endian bytes with trailing zero bytes trimmed, and the output being spent was confirmed at least 6 blocks before the etching block (COMMIT_CONFIRMATIONS = 6).

ord Source: src/index/updater/rune_updater.rs

R29: Reserved name assignment for unnamed etchings

[6. Etching]

An etching without a name is assigned a reserved name by the indexer: 6402364363415443603228541259936211926 + (block << 32 | tx), where block and tx are the etching's rune ID components. Reserved-name etchings need no commitment.

ord Source: src/index/updater/rune_updater.rs

R30: Name length unlock schedule

[6. Etching]

Name unlock schedule, mainnet: runes activate at block 840,000 (first_rune_height = 4 * 210,000). At activation, names of 13 letters and longer are unlocked. The minimum steps down through the length thresholds every 17,500 blocks (one twelfth of a halving interval), interpolating linearly between thresholds, until every name, including single letters, is unlocked at block 1,050,000. Before activation no etching is honored.

ord Source: crates/ordinals/src/rune.rs
Commitment Requirement (Rule R27)

Any non-reserved rune name requires a prior Taproot commitment transaction confirmed at least 6 blocks prior. Revealing the etching earlier causes the name to be silently disregarded and replaced with a reserved sequence name.

7. Minting

A transaction may mint units of an active, open-mint rune using Tag 20.

R31: Mint tag arity and bounds

[7. Minting]

The Mint tag (20) is given twice: the first value is the block and the second the transaction index of the rune ID to mint. Values must fit u64 and u32 respectively, and block 0 with a nonzero tx is invalid. Values failing these checks are left unconsumed and make the transaction a cenotaph via R17. A single Mint value with no pair behaves the same way.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: UnrecognizedEvenTag

R32: Mint terms evaluation rules

[7. Minting]

A mint succeeds when the target rune exists and its terms are satisfied at the mint transaction's block height: the height is not below the mint's start, is below the mint's end, and the recorded number of mints is below the cap (a missing cap is 0, so a rune without terms or cap is unmintable). Start is the later of HeightStart and etching block + OffsetStart; end is the earlier of HeightEnd and etching block + OffsetEnd; whichever of the pair is absent does not constrain.

ord Source: src/index/updater/rune_updater.rs

R33: Mint accounting and silent failure

[7. Minting]

A successful mint increments the rune's mint count and adds the fixed amount (Amount at etching, 0 if absent) to the transaction's unallocated runes. A mint whose terms are not satisfied is simply ignored: it is not a cenotaph and does not count toward the cap. A mint in a transaction that is a cenotaph for other reasons does count toward the cap, and its output is burned (R45).

ord Source: src/index/updater/rune_updater.rs

8. Edicts

Edicts transfer rune balances from the transaction unallocated pool to specific output indices.

R34: Edict quadruple and delta encoding

[8. Edicts and delta encoding]

Each edict is four integers: block delta, transaction index or delta, amount, output. A running rune ID starts at 0:0. The block delta is added to the running block. If the block delta is 0, the transaction value is added to the running transaction index; if the block delta is nonzero, the transaction value is the absolute transaction index. Encoders must sort edicts by rune ID for this encoding to be compact; decoders reconstruct absolute IDs by accumulation.

ord Source: crates/ordinals/src/rune_id.rs

R35: Rune ID 0:0 refers to current etching

[8. Edicts and delta encoding]

The resulting ID 0:0 refers to the rune etched by this very transaction. If the transaction etches no rune (or the etching was disregarded under R28), such an edict is skipped without effect.

ord Source: src/index/updater/rune_updater.rs

R36: Invalid edict ID produces EdictRuneId flaw

[8. Edicts and delta encoding]

If ID accumulation overflows (block above u64, transaction index above u32) or produces block 0 with a nonzero transaction index, the transaction is a cenotaph with flaw EdictRuneId. Edict parsing stops at the first failure.

ord Source: crates/ordinals/src/runestone/message.rs Violating Flaw: EdictRuneId

R37: Edict output bounds and EdictOutput flaw

[8. Edicts and delta encoding]

The edict output must fit u32 and must be at most the transaction's output count. An output greater than the output count makes the transaction a cenotaph with flaw EdictOutput.

ord Source: crates/ordinals/src/runestone/message.rs Violating Flaw: EdictOutput

R38: Edict execution, sweeping, and splits

[8. Edicts and delta encoding]

Edicts are processed in order against the unallocated pool. An amount of 0 means the edict's entire remaining balance of that rune. A nonzero amount is clamped to the remaining balance. An edict output exactly equal to the output count is a split: with amount 0, the remaining balance is divided evenly over all non-OP_RETURN outputs, earlier outputs receiving the remainder one unit at a time; with a nonzero amount, that amount is allocated to each non-OP_RETURN output in order until the balance runs out.

ord Source: src/index/updater/rune_updater.rs

9. Pointer

Tag 22 specifies which output index receives all unallocated remainder balances after all edicts execute.

R39: Pointer destination and default fallback

[9. Pointer]

The Pointer (tag 22) must fit u32 and be strictly less than the output count; otherwise its value is unconsumed and the transaction is a cenotaph via R17. After all edicts are processed, remaining unallocated runes go to the pointer output. Without a pointer they go to the first non-OP_RETURN output. If no non-OP_RETURN output exists, they are burned.

ord Source: crates/ordinals/src/runestone.rs Violating Flaw: UnrecognizedEvenTag

10. Allocation & State Machine

The deterministic allocation state machine rules R40 through R44 govern UTXO rune balances.

R40: Unallocated pool composition

[10. State transitions]

A transaction's unallocated pool is the sum of: rune balances on every spent input outpoint, plus the minted amount when the runestone mints successfully, plus the premine when it etches.

ord Source: src/index/updater/rune_updater.rs

R41: OP_RETURN burns

[10. State transitions]

Allocations assigned to an OP_RETURN output are burned, whether they got there by edict or by pointer. This is the deliberate burn mechanism.

ord Source: src/index/updater/rune_updater.rs

R42: Default transfer without runestone

[10. State transitions]

A transaction with rune inputs and no runestone at all transfers every input rune balance to its first non-OP_RETURN output. Runes never disappear silently: every unit is either allocated to an output or recorded as burned.

ord Source: src/index/updater/rune_updater.rs

R43: Rune ID permanence

[10. State transitions]

A rune's ID is assigned at etching: the etching block height and the transaction's index within that block, written BLOCK:TX. IDs are permanent and never reassigned.

ord Source: src/index/updater/rune_updater.rs

R44: Outpoint balances and atomic units

[10. State transitions]

Balances are per rune, per outpoint, in atomic units (u128). An outpoint may carry balances of any number of runes. Spending the outpoint releases all of them into the spending transaction's unallocated pool.

ord Source: src/index/updater/rune_updater.rs

11. Cenotaphs & Flaw Reference

A cenotaph is a malformed runestone. When a cenotaph is detected, the transaction loses all input rune balances.

Total Destruction on Malformation (Rule R45)

All input runes entering a cenotaph transaction are permanently burned. They cannot be recovered, redirected, or spent. Any etching becomes unmintable, and any mint is burned.

R45: Cenotaph consequences

[11. Cenotaphs]

A cenotaph is a runestone that violates any rule marked above as producing one. In a cenotaph transaction: every input rune balance and every minted or premined amount is burned; a mint still increments the target rune's mint count; and an etching (if its name is valid and committed under R28) still creates the rune, but with no recorded divisibility, symbol, spacers, premine, or terms, and permanently unmintable.

ord Source: src/index/updater/rune_updater.rs

R46: Upgrade mechanism through forward compatibility

[11. Cenotaphs]

Cenotaphs are the protocol's forward-compatibility mechanism. Future upgrades may assign meaning to currently unrecognized even tags and flags. Unupgraded clients, applying these rules, will treat upgraded runestones as cenotaphs and report the affected runes as burned rather than misreporting who owns them.

ord Source: crates/ordinals/src/runestone.rs

R47: First flaw reported

[11. Cenotaphs]

Only the first flaw encountered is reported by the reference implementation, but any single flaw is sufficient: cenotaph status is not a matter of degree.

ord Source: crates/ordinals/src/runestone.rs
